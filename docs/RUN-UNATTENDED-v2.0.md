## 0. 优先级裁决顺序（最重要，v1.0 缺失）

当「更严谨」与「更快交付」冲突时，按此顺序裁决：

1. **正确性**：SDD 口径不得偏离、金额整数精确、比率 1e-12、无静默降级 —— 不可让步
2. **交付进度**：墙钟预算 —— 在 1 满足后**优先于 3**
3. **证据完备度**：留档、复核深度 —— **够用即止，不得无限加固**

v1.0 把 3 隐含排在 2 之前（「无实测证据一律 ❌」「每项 ✅ 且附证据」），这是 13 小时只走 9.6% 的直接原因。**证据是为可审计服务的，不是为自证服务的。**

## 1. 每任务硬预算（超出即违规，主控必须打断）

| 项 | C1 | C2 | C3 |
|---|---|---|---|
| 墙钟时间 | ≤ 20 min | ≤ 45 min | ≤ 90 min |
| 新增生产代码 | ≤ 150 行 | ≤ 400 行 | ≤ 700 行 |
| 新增测试函数 | ≤ 8 | ≤ 25 | ≤ 40 |
| hypothesis 属性 | 0 | ≤ 3 条 | ≤ 6 条（开发期 `max_examples=25`，只在 S9 的 V-2 门禁跑 500） |
| 单个证据文件 | ≤ 60 行 | ≤ 120 行 | ≤ 200 行 |
| ADR | 0（要点写进 commit message） | ≤ 1 份 ≤ 40 行 | ≤ 1 份 ≤ 60 行 |
| 复核档案 | 无 | 无（并入阶段末批量复核） | ≤ 1 份 ≤ 80 行 |

**超时 / 超量处置**：立即交付当前**最小可用版本**，在 `ops/blockers.md` 登记一条 TODO（缺什么 / 影响 / 补做条件），然后进入下一任务。**禁止为「更完整」继续磨。**

## 2. 仪式按档分级（替代 v1.0「所有任务都走 7 步 6 角色」）

| 档 | 取证 | 测试 | 实现 | 复核 | 提交 |
|---|---|---|---|---|---|
| **C1** | 主控直接给行号摘录，**不派 R1** | 与实现同一 agent | 同 | **不派 R4**，主控抽查 diff | 同 agent |
| **C2** | 同上 | 同实现 agent，先写关键负向用例 | 同 | **阶段末批量 R4 一次**（覆盖该阶段全部任务） | R5 |
| **C3** | R1 出 digest（≤120 行） | R3 先写 RED | R2 | 每任务 R4（档案 ≤80 行） | R5 |

并发 ≤ 3；同文件写集不得并行；S1 与 S8 严格串行。
**一个 C1 任务派 5 个 agent 是事故，不是严谨。**（v1.0 的 S1-T01 是 C1 取证任务，却走了 3 轮 + 产 5 份 digest 373 行 + 9 份 ADR，耗时 28 分钟。）

## 3. RED-first 只对算法模块强制

**必须先 RED 后 GREEN** 的模块（白名单）：`attainment` `normalize` `grading` `evidence` `redline` `pooling` `sensitivity` `triangulation` `diagnostics` `weights_ahp` `weights_combine` `weights_calibrate` `whatif` `audit`（哈希与规范化序列化）。

**声明式契约层不强制 RED**：`models.py` `config.py` `io_loaders.py` `cli.py` `reports.py` —— 实现后写「契约测试 + 负向测试」即可。
理由：pydantic 的 `frozen` + `extra='forbid'` 本身就是契约保证；v1.0 对 models.py 先写 602 个失败测试、留下 **1,376,802 B / 32,129 行**的失败输出，是纯浪费。

## 4. 禁止自创验证层（白名单制）

只允许 SDD 明确要求的四类对拍 / 守护：

1. **手算对拍**：AHP（几何平均 vs 特征向量，差 ≤1e-6）、熵权、TOPSIS、GRA、VIF、Spearman（差 ≤1e-12）
2. **mock 断言 INV-3**：`aggregate` 不得调用 `diagnostics` / `weights_combine`
3. **目录哈希比对 INV-2**：`whatif` 不污染生产输出
4. **同 seed 逐字节相等**：`fixtures_gen` / MC / `weights_calibrate`

**禁止**：mutation testing、anti-cheat diff、自建 probe 脚本、为交叉验证而重复实现参考算法（SDD 点名要求的双算法对拍除外）。
实测：前 13 小时这类自创验证产出 **>120 KB** 档案（L4-mutation 34 KB、L4-anticheat-diff 14 KB、L4-probe-api 16 KB、L4-probe-io 12 KB…），`quality_incidents = 0`，即**零缺陷发现**。

## 5. 收敛判据（新增第 5 条「够用即止」）

满足即**立刻**进入下一任务，禁止追加加固轮次：

1. 本任务验收清单全 ✅
2. 全量 pytest 0 failed / 0 error
3. 无新增 `skip` / `xfail`
4. 编码校验通过（无 BOM / LF / 无 TAB）
5. **产物在 §1 预算内**

## 6. 证据与状态瘦身规则

- `ops/evidence/` **加入 `.gitignore`**；仓库里只保留 ≤200 行的摘要。原始 pytest 全量输出**不落盘**——需要时只记「失败 N 项 + 前 20 行 + 统计行」。（v1.0 已把 **2,024,190 B** 转储提交进 git 历史。）
- `ops/dag-state.json` 的 `evidence` 字段**只存数字**：`tests_passed / duration_s / prod_lines / test_funcs / commit`。禁止塞文本块。整份状态文件目标 ≤ 25 KB（v1.0 已膨胀到 59,348 B）。
- 阶段对账单 ≤ 40 行（七段保留，每段 ≤6 行）。
- 一任务一 commit；裁决要点写进 commit message，**除 C3 外不单开 ADR**。
