# ORCH-10 digest 的取用方式：子 agent 直接读 digest 文件，主控只持摘要与存疑段

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-23 |
| 阶段 / 任务 | 全阶段（S1~S9） |
| 裁决人 | Orchestrator（主控） |
| 类型 | 流程裁决（§11-2 与 §1.2-3 的适用优先序） |

## 冲突

ORCH §11-2（Token 纪律，标注「强制」）要求「派工时**把 digest 内容直接嵌进子任务 prompt**，
不让子 agent 自己去读文件」；而 §1.2-3 规定「后续所有角色（含复核）**只读 digest**，不读原文」
——后者明文把 digest 设定为各角色的读取对象。

## 裁决

子 agent 派工时给出 digest 的**绝对路径清单**并令其自行读取；主控不复述 digest 全文，
只在需要裁决时取用相关段落。

## 理由（以 §11-2 自身的立法目的为准）

§11-2 的目的是**省 token**。设单个 digest 约 2k token：
- 内嵌方案：主控需先持有 2k，再在 R3 / R2 / R4 三次派工中各重复输出 2k = 主控侧 8k，
  且这 2k 会**永久占据主控上下文**；
- 读文件方案：每个子 agent 各自读入 2k（在**它自己的**上下文里，用完即弃），主控侧 0k。

本项目是 S1~S9 共 52 任务的长程无人值守，**主控上下文是唯一不可再生的稀缺资源**
（§8.1 明确「单个会话跑不完 52 个任务」）。把 digest 常驻主控上下文会显著提前触发交接，
与 §11-2 的目的相悖。故按目的解释优先于字面解释。

## 不被本裁决放宽的项

- 子 agent **仍严禁读 SDD 原文**（§1.2-3），只准读 `docs/digest/`；派工 prompt 中显式重申此禁令。
- R4 的输入仍严格限定为 digest + pytest 输出 + `git diff`（§4），不得读实现者推理。
- 主控裁决口径争议时，仍以 digest 中的 SDD 原文行号为唯一依据（H-10 / H-11）。

## 依据

ORCH §1.2-3、§11-2、§8.1、§4、§2 H-10/H-11。
